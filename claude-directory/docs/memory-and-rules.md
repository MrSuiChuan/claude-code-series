# Memory and Rules

这份文档解释 `claude-directory` 里几种“长期指令”应该怎么分工：

- `CLAUDE.md`
- `.claude/rules/`
- `.claude/agent-memory/`

它们看起来都像“给 Claude 的说明”，但用途并不一样。
如果混着用，结果通常是：

- 总提示越来越长
- 局部规则污染全局上下文
- 本该长期积累的经验被写成僵硬规则
- 本该稳定执行的规则却被塞进 memory

## 一句话分工

- `CLAUDE.md`：项目级总约定
- `.claude/rules/`：专题规则和局部规则
- `.claude/agent-memory/`：某个角色长期积累的经验、偏好和历史线索

一个简单判断方法是：

- 对整个项目都长期成立，放 `CLAUDE.md`
- 只对某类任务或某些目录成立，放 `rules/`
- 会随着任务推进逐步积累、更新，放 `agent-memory/`

## `CLAUDE.md` 负责什么

`CLAUDE.md` 应该只放项目最核心、最稳定的约定。

适合放这里的内容：

- 项目是什么
- 技术栈和主要边界
- monorepo 分层，例如 `apps/web`、`apps/api`、`packages/contracts`、`tests/e2e` 分别负责什么
- 工作方式原则
- 常用命令
- 编码和测试总规则
- 评审时最常检查的项目级问题

这些内容应该满足一个原则：

- 即使是第一次进入项目的人，也应该先看到这层信息

不适合放这里的内容：

- 某个具体功能的细碎规则
- 某个目录独有的实现惯例
- 某个角色的评审偏好
- 会频繁变化的任务经验

## `rules/` 负责什么

`.claude/rules/` 适合放“专题化、结构化”的规则。
它的价值不在于比 `CLAUDE.md` 更高级，而在于它更容易拆分和维护。

适合放进 `rules/` 的内容：

- 前端 UI 规则
- API 设计规则
- 共享契约规则
- 表单和校验规则
- Prisma 和数据库规则
- 性能和缓存规则
- 测试规则
- 安全和密钥规则

这类规则通常有两个特点：

- 它们很重要，但不是所有任务都要同时看
- 它们会随着技术栈演进而独立调整

## 为什么不要把所有规则都塞进 `CLAUDE.md`

如果所有规则都堆到一个文件里，常见问题是：

- 文件太长，真正重要的约定被淹没
- 局部规则影响所有会话
- 调整一个小专题时，必须改大文件
- 团队很难判断“哪些是全局规则，哪些只是局部做法”

更好的做法是：

- `CLAUDE.md` 只保留项目总约定
- `rules/` 承接专题规则
- `commands`、`agents`、`skills` 各自承担流程和角色职责

## `rules/` 里的规则应该怎么写

一个好的规则文件通常应该：

- 聚焦一个主题
- 用简洁的检查项表达
- 避免和别的规则重复
- 尽量描述稳定模式，而不是一次性任务要求

例如，前端 UI 规则里适合写：

- 先复用现有 layout 和基础组件
- loading、empty、error state 要显式处理
- 兼顾移动端和桌面端
- 不要把服务端逻辑泄露到 client component

而共享契约规则里适合写：

- `packages/contracts` 里统一维护 schema、DTO 和导出的类型
- `apps/web` 和 `apps/api` 不各自复制一份请求 / 响应结构
- 契约变更时同步检查前端调用和后端实现

但不适合写：

- “把这次订单页面做成左侧筛选右侧表格”
- “这个页面先别动弹窗”
- “本周临时使用某个视觉方案”

后面这类更像任务要求，不是长期规则。

## `agent-memory/` 负责什么

`.claude/agent-memory/` 适合存某个 agent 长期积累下来的经验。
它不是项目规则库，而更像“角色工作笔记”。

适合放进 agent memory 的内容：

- 这个 reviewer 经常发现的高频问题
- 某类改动在这个项目里常见的隐性风险
- 某条链路的历史坑点
- 某角色在这个仓库里需要优先关注的信号

例如：

- `frontend-reviewer` 记住这个项目经常缺 loading state
- `backend-reviewer` 记住接口经常把权限判断漏在 service 层
- `backend-reviewer` 记住这个仓库里契约升级后最容易漏改 `apps/api` 的返回结构
- `e2e-reviewer` 记住几个关键链路最容易断在登录态或异步刷新

## 什么不应该放进 memory

以下内容更适合放进 `CLAUDE.md` 或 `rules/`，而不是 memory：

- 项目总原则
- 技术栈说明
- 长期不变的安全要求
- 稳定的 API 设计规范
- 固定的测试命名规则

原因很简单：

- memory 是累积性的
- 规则是规范性的

如果把规范性内容塞进 memory，后续会越来越混乱。

## memory 和 rules 的区别

可以把它们理解成两种不同的问题：

- `rules` 回答的是：“这个项目通常要求怎么做？”
- `memory` 回答的是：“这个角色在这个项目里已经观察到了什么？”

前者更像制度，后者更像经验。

## 推荐的使用方式

### 项目启动阶段

先写好：

- `CLAUDE.md`
- `rules/` 的核心专题文件

这一步解决的是项目基本约束。

### 模板逐渐成熟后

再为高价值角色建立 memory，例如：

- `frontend-reviewer`
- `backend-reviewer`
- `accessibility-reviewer`
- `e2e-reviewer`

这一步解决的是“角色长期复盘”和“评审质量累积”。

### 任务进行中

如果某个问题只是当前任务的临时上下文，不要立刻写进 rule 或 memory。
先观察它是不是会重复出现。

## 什么时候该新增一个 rule

满足以下条件时，通常值得新增：

- 某类问题重复出现
- 这个问题有稳定、可表达的处理原则
- 它不只是某个角色的个人经验
- 它足够长期，不会几天后就失效

例如：

- 多次出现输入校验缺失
- 多次出现 client/server 边界混乱
- 多次出现测试遗漏 loading state

## 什么时候该新增一条 memory

满足以下条件时，通常值得新增：

- 这是某个角色反复遇到的信号
- 它更像经验提醒，而不是硬性规则
- 它对后续类似任务有帮助
- 它依赖项目历史，而不是单纯的规范

例如：

- “这个项目的表格页经常漏掉空态”
- “这个模块的权限判断经常散落在入口之外”
- “这个仓库的关键链路回归测试最常断在会话刷新后”

## 推荐实践

- `CLAUDE.md` 只写项目总约定，不要越写越像百科全书
- `rules/` 按主题拆分，保持文件职责单一
- `memory` 记录经验，不替代规则
- 先观察重复模式，再决定是否沉淀
- 当一个 memory 已经变成稳定规范时，考虑上移到 `rules/`

## 总结

可以把三者的关系压缩成一句话：

- `CLAUDE.md` 负责讲“这个项目总体怎么做”
- `rules/` 负责讲“某类问题具体怎么做”
- `agent-memory/` 负责讲“这个角色在项目里已经学到了什么”

当这三层分工清楚时，项目级配置才会既稳定又可演化。
