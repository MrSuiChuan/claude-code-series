# Global vs Project Scope

这份文档解释 Claude Code 配置里一个最容易混淆的问题：

- 什么应该放项目仓库里
- 什么应该放用户自己的全局目录里
- 什么虽然有用，但不适合做成团队默认模板

如果这层边界不清楚，常见结果是：

- 项目仓库里混入大量个人偏好
- 团队级模板背上本不该共享的配置
- 新同事分不清哪些目录可以提交，哪些不能提交
- 高级能力和项目模板纠缠在一起，后期越来越难维护

## 一句话判断

- 跟当前仓库长期绑定的，放项目目录
- 跟某个用户账号、个人习惯或跨项目工作方式绑定的，放全局目录
- 只有少数人会用、而且不适合作为团队默认值的，写进文档说明，不直接塞进模板

## 项目层通常放什么

项目层的目标是：

- 换一个人拉下仓库，核心行为基本一致
- 新开一个 worktree 或新建一个开发环境时，项目规则仍然可复用

适合放在项目仓库里的内容通常包括：

- `CLAUDE.md`
- `.claude/rules/`
- `.claude/commands/`
- `.claude/skills/`
- `.claude/agents/`
- `.claude/agent-memory/`
- `.claude/hooks/`
- `.claude/settings.json`
- `.mcp.json`
- `.worktreeinclude`

这些内容回答的都是类似问题：

- 这个项目通常怎么做
- 这个项目有哪些高频入口
- 这个项目的评审视角是什么
- 这个项目的运行边界和自动化动作是什么

## 全局层通常放什么

全局层的目标是：

- 让某个用户跨多个项目保持稳定工作方式
- 保存不适合提交到仓库的个人配置

适合放在用户全局目录里的内容通常包括：

- 用户级 settings
- 用户级 MCP 配置
- 跨项目复用的个人 skills
- 个人快捷命令或个人风格 output style
- 用户自己的 task / team / automation 组织方式
- 个人本地实验性配置

这些内容更像是在回答：

- 这个用户平时喜欢怎么工作
- 这个用户跨项目共用哪些能力
- 这个用户要不要启用某些高级机制

## 什么最容易被误放进项目仓库

下面这些东西最容易“看起来很有用”，但其实不一定该直接放进模板：

- 个人快捷键或 shell alias 习惯
- 绑定本机路径的本地脚本
- 某个账号专用的 MCP 接入
- 个人任务管理目录
- 跨项目复用、但和当前仓库无关的 skill
- 只适用于某个维护者的重型 settings

判断方法很简单：

- 如果删掉它，别人仍然能在这个项目里正常协作，它大概率就不该进项目模板

## 哪些高级能力更适合“文档说明”，而不是“默认模板”

有一些能力很值得知道，但不适合直接放进 `project-root/`：

- 任务系统
- agent teams
- 用户级自动记忆
- 大量跨项目的个人 commands
- 强个人风格的 settings

原因不是它们不重要，而是：

- 它们更偏用户工作方式
- 团队不一定达成统一
- 一旦默认塞进模板，会增加认知成本和维护成本

更好的做法是：

- 在 `docs/` 里说明这些能力存在
- 解释什么时候值得启用
- 由具体团队或个人决定是否落地

## 项目模板应该克制到什么程度

一个健康的项目模板通常只默认放三类东西：

1. 项目级总约定
2. 高频协作入口
3. 团队普遍接受的运行边界

它不应该默认承载：

1. 用户个人工作台
2. 跨项目任务中台
3. 某个维护者的完整本地环境偏好

## 常见例子

### 例子 1：项目规则

“接口变更要同步检查前端、共享契约和后端实现”

这显然应该放项目层，因为它只对这个仓库的协作方式有意义。

### 例子 2：个人快捷命令

“我希望所有项目都能快速调用我的个人研究命令”

这更适合放全局层，因为它不是当前项目必须知道的内容。

### 例子 3：高级任务协作

“团队可能未来会用 task 系统和 agent teams”

这适合先写在文档里，作为进阶能力说明，而不是现在就放进模板默认目录。

## 推荐实践

- 先把项目模板做小，保证新读者能快速理解
- 把强团队相关的内容放项目层
- 把强个人相关的内容放全局层
- 把高级但非默认能力写进 `docs/`
- 当某项高级能力已经成为团队稳定习惯，再考虑是否进入项目模板

## 和本模板的关系

`claude-directory/project-root/` 的定位是：

- 提供一套可提交、可协作、可复制的项目模板

它的定位不是：

- 替代用户自己的全局工作台
- 替代个人长期任务系统
- 替代所有跨项目的个人偏好配置

理解这层边界后，`project-root/` 才能长期保持清晰和克制。
