为 $ARGUMENTS 完成页面交付。

目标不是只把页面“做出来”，而是让它在当前项目里看起来像原生的一部分，并在结构、状态、响应式和可访问性上达到可交付标准。

执行流程：

1. 先看附近已有实现：
   - `apps/web` 中相邻页面和 layout 的结构
   - 现有页面的视觉模式
   - 已有基础组件和组合方式
   - 数据获取和状态处理的惯例
   - 是否已经有对应的共享契约和 API client

2. 调用 `scaffold-page` skill，构建页面或 route segment：
   - 复用现有 UI 基础组件和布局模式
   - 数据请求优先走统一 API client 和共享契约
   - 共享逻辑提取到可复用组件或前端共享模块
   - 不为单个页面发明新的架构层

3. 检查页面状态完整性：
   - loading state
   - empty state
   - error state
   - 成功态和边界态是否清楚

4. 检查实现复杂度：
   - 是否引入了不必要的 client component
   - 是否重复编排了已有视图逻辑
   - 是否把只适合后端的逻辑放进了前端组件

5. 调用 `ui-review` skill，重点检查：
   - 布局和视觉一致性
   - 响应式表现
   - loading、empty、error state 是否齐全
   - 客户端复杂度是否过高

6. 调用 `accessibility-reviewer`，重点检查：
   - 语义结构
   - 键盘可达性
   - 焦点顺序和交互反馈
   - 表单控件和可读性

7. 输出交付总结：
   - 入口文件和主要改动点
   - 仍需补充的测试
   - 尚未覆盖的风险或限制
   - 如果当前实现已经足够稳，明确说明可以进入后续联调或评审

工作原则：

- 优先复用现有 layout、component 和交互模式
- 同时兼顾桌面端和移动端
- 页面级问题优先在页面层解决，通用问题再提取
- 不要为了“更优雅”而偏离项目现有模式
- 输出时先给问题，再给改进建议
