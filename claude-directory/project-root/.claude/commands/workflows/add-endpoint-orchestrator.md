为 $ARGUMENTS 完成接口交付。

目标不是只把 endpoint 写出来，而是让它在当前项目里符合既有的请求边界、校验方式、错误处理习惯和安全要求。

执行流程：

1. 先查看附近已有实现：
   - `apps/api` 中相邻请求入口或接口入口
   - 输入校验和返回结构的既有模式
   - 认证、授权、限流、中间层复用方式
   - 领域逻辑是否已存在于可复用业务模块
   - 是否已经有可复用的 `packages/contracts` 契约

2. 调用 `scaffold-api-route` skill，完成接口骨架设计：
   - 确认正确的接口入口位置
   - 定义请求和响应结构
   - 尽量复用或新增 `packages/contracts` 中的共享契约
   - 校验所有不可信输入
   - 尽量把业务逻辑放在可复用层，而不是直接堆在入口文件

3. 检查接口边界是否完整：
   - 参数校验是否明确
   - 错误返回是否与项目习惯一致
   - 是否需要 auth、授权或限流
   - 是否有日志、观测性或失败路径遗漏

4. 如果涉及数据库 schema、migration 或数据一致性，调用 `db-migration-review`

5. 如果接口涉及安全敏感信息、权限边界或外部输入处理，调用 `security-review`

6. 调用 `backend-reviewer`，重点检查：
   - 请求边界是否清楚
   - 共享逻辑是否正确下沉
   - 错误处理是否稳定
   - 类型与运行时校验是否一致
   - 是否偏离附近模块的实现模式

7. 输出交付总结：
   - 入口文件和核心逻辑位置
   - 契约定义位置
   - 请求与响应结构摘要
   - 需要补充的测试
   - 风险点、权限点和未验证项

工作原则：

- 优先沿用附近接口的实现模式
- 入口文件负责边界，业务逻辑尽量下沉到可复用层
- 所有不可信输入都要校验
- 不要把关键逻辑藏在 controller 或 route 文件的细碎分支里
- 输出时先给问题，再给改进建议
