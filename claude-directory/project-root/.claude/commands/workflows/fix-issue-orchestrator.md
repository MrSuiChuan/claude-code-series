处理 bug：$ARGUMENTS

你的目标不是立刻改代码，而是先用最小成本收敛到最可能的根因，再给出最小且安全的修复方案。

执行流程：

1. 先把问题重新描述清楚：
   - 预期行为是什么
   - 实际行为是什么
   - 影响范围大概在哪里
   - 如果用户描述不完整，明确列出当前假设

2. 查看附近实现，确认最可能的入口：
   - 前端页面、组件、交互入口
   - route handler、server action、API route
   - `src/lib`、数据库访问层、第三方集成层
   - 测试或日志里已有的相关线索

3. 调用 `bug-triage` skill，完成初步问题收敛：
   - 复述问题
   - 找出最可能的入口位置
   - 沿 UI、API、数据层追踪链路
   - 收敛到最可能的根因
   - 给出最小安全修复方案
   - 建议一条最小回归测试

4. 根据问题类型选择评审角色：
   - 如果问题偏前端交互、状态、布局、可访问性，调用 `frontend-reviewer`
   - 如果问题偏接口、权限、数据库或服务端逻辑，调用 `backend-reviewer`
   - 如果问题涉及键盘操作、语义结构、焦点管理，调用 `accessibility-reviewer`
   - 如果问题是关键用户链路失效，调用 `e2e-reviewer`

5. 汇总结论并输出：
   - 最可能根因
   - 证据链或推断链
   - 最小修复方案
   - 建议补充的回归测试
   - 风险点和未验证项

工作原则：

- 优先做最小改动，不轻易扩大范围
- 先沿用附近文件已有模式，不随意引入新抽象
- 不要在证据不足时装作已经确认根因，要明确说出“已确认”和“推测”的边界
- 如果存在多个合理根因候选，按概率排序
- 输出时先给问题，再给修复建议
