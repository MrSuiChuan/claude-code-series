# Page Shipping Workflow

这份文档说明网页系统里一个页面从“提出需求”到“可以交付评审”的推荐流程。

它不是在替代项目自己的开发流程，而是在说明当前 `claude-directory` 这套 `command`、`agent`、`skill` 配置应该如何协作。

## 目标

页面交付不只是把 UI 结构拼出来，还包括：

- 沿用已有页面模式
- 状态完整
- 响应式可用
- 可访问性不过关的地方尽量提前发现
- 输出结果足够容易进入后续评审和联调

## 参与角色

在这个工作流里，三类构件承担不同职责：

- `command`
  作为工作流入口，负责组织步骤
- `skill`
  负责页面搭建和 UI 检查这类可复用任务
- `agent`
  负责用稳定的评审视角检查问题

建议组合如下：

- `ship-page`
- `scaffold-page`
- `ui-review`
- `accessibility-reviewer`

## 推荐流程

### 阶段 1：理解附近模式

在真正改页面前，先看清楚附近已有实现：

- 相邻 route 和 layout
- 现有组件组织方式
- 视觉和交互模式
- 数据获取和状态处理惯例

这一阶段的目标不是开始写代码，而是避免一上来就偏离项目现有风格。

### 阶段 2：生成页面骨架

由 `ship-page` 调用 `scaffold-page`，完成页面的第一版结构。

这一步应该优先保证：

- route 位置正确
- layout 层次合理
- 默认优先 server component
- 复用已有基础组件
- 共享逻辑不要直接散落在页面入口文件里

### 阶段 3：补全页面状态

页面骨架出来以后，优先检查状态完整性，而不是急着追求视觉细节。

至少要显式考虑：

- loading state
- empty state
- error state
- 成功态下的主路径是否清晰

如果这些状态缺失，页面通常还不算可交付。

### 阶段 4：做 UI 质量检查

由 `ship-page` 调用 `ui-review`，重点检查：

- 与附近页面的视觉一致性
- 响应式表现
- 过度客户端化的问题
- 重复视图逻辑
- 状态呈现是否完整

这一步的目标，是让页面不仅“能用”，而且“像这个项目自己的页面”。

### 阶段 5：做可访问性检查

由 `ship-page` 调用 `accessibility-reviewer`，重点检查：

- 语义结构
- 键盘操作
- 焦点顺序
- 表单控件可读性
- 交互反馈是否足够明确

这一步适合在视觉结构已基本稳定后执行。

### 阶段 6：输出交付总结

最后由 workflow 统一输出：

- 页面入口和主要改动点
- 还需要补的测试
- 仍未覆盖的风险
- 是否适合进入后续评审或联调

## 工作流示意

```text
User Request
  -> ship-page (command)
  -> scaffold-page (skill)
  -> ui-review (skill)
  -> accessibility-reviewer (agent)
  -> Delivery Summary
```

如果写得更细一点，可以理解为：

```text
需求
  -> 看附近实现
  -> 生成页面骨架
  -> 补全 loading / empty / error
  -> 检查 UI 一致性与响应式
  -> 检查可访问性
  -> 输出交付总结
```

## 什么时候适合用这个 workflow

以下场景很适合：

- 新增一个页面
- 重构一个旧页面
- 新增一个 route segment
- 为现有页面补状态和交互完整性
- 在进入评审前做一次结构化检查

## 什么时候不必强行使用

以下场景可以简化处理：

- 只改一个非常局部的文案或样式
- 只改一个独立小组件，不涉及页面交付
- 只是快速验证一个视觉想法
- 只是排查一个明确的页面 bug

这时可以直接用更小粒度的 command 或 skill，而不必完整走一遍页面交付流程。

## 推荐实践

- 先复用附近已有模式，再决定是否抽象
- 先补状态完整性，再做细节 polish
- UI 评审和可访问性评审最好分开做
- workflow 输出要明确列出未验证项，不要假装所有问题都已经解决
- 如果页面涉及关键用户链路，后续应补测试或联调验证

## 总结

这个 workflow 的核心价值，不是让页面开发“更复杂”，而是让页面从一开始就朝着“可交付”推进。

如果把职责压缩成一句话：

- `ship-page` 负责组织交付流程
- `scaffold-page` 负责把页面搭出来
- `ui-review` 负责检查它像不像这个项目自己的页面
- `accessibility-reviewer` 负责补上容易被忽略的可用性问题

这样组合起来，页面工作流就会比单独写一个 prompt 更稳定，也更容易复用。
