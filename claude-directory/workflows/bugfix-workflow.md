# Bugfix Workflow

这份文档说明网页系统里一个 bug 从“收到问题描述”到“形成可执行修复方案”的推荐流程。

它不是要求所有 bug 都走同样重的流程，而是给 `claude-directory` 里的 `command`、`skill`、`agent` 提供一个稳定的协作方式。

## 目标

一个好的修复流程，不只是尽快改代码，还应该做到：

- 先把问题说清楚
- 找到最可能的入口和传播链路
- 区分“已确认根因”和“高概率推断”
- 优先给出最小且安全的修复方案
- 明确测试建议和未验证项

## 参与构件

推荐组合如下：

- `fix-issue-orchestrator`
- `bug-triage`
- `frontend-reviewer`
- `backend-reviewer`
- `accessibility-reviewer`
- `e2e-reviewer`

其中：

- `command` 负责组织排查和汇总结论
- `skill` 负责收敛问题链路
- `agents` 负责从不同专业视角判断风险和修复方向

## 推荐流程

### 阶段 1：重新表述问题

先把收到的问题描述重新说清楚：

- 预期行为是什么
- 实际行为是什么
- 影响范围大概在哪里
- 当前有哪些假设，哪些信息还缺失

这一步很重要，因为很多 bug 的第一版描述其实混杂了现象、猜测和结论。

### 阶段 2：找到入口

在真正给结论前，先查看最可能的入口位置：

- 页面或组件入口
- route handler 或 server action
- `src/lib` 里的共享逻辑
- 数据访问层
- 第三方集成层
- 相关测试、日志、报错信息

这一步的目标不是遍历整个仓库，而是尽快缩小搜索空间。

### 阶段 3：问题收敛

由 `fix-issue-orchestrator` 调用 `bug-triage`，沿着链路做结构化分析：

- 先复述问题
- 找出最可能的入口
- 沿 UI、API、数据层追踪
- 列出最可能的根因
- 给出最小安全修复方案
- 建议最小回归测试

这一步的重点是“收敛”，不是“立刻全面重构”。

### 阶段 4：按问题类型调对应 reviewer

如果问题偏前端：

- 调用 `frontend-reviewer`

如果问题偏接口、权限、数据库、服务端逻辑：

- 调用 `backend-reviewer`

如果问题涉及语义结构、焦点、键盘交互：

- 调用 `accessibility-reviewer`

如果问题在关键用户链路上，或需要判断是否该补端到端回归：

- 调用 `e2e-reviewer`

这一步的目标，是用不同角色把修复方案看得更稳，而不是只靠一个通用结论。

### 阶段 5：输出修复结论

最后由 workflow 统一输出：

- 最可能根因
- 证据链或推断链
- 最小修复方案
- 建议补充的测试
- 风险点和未验证项

如果根因还没被完全确认，也应该明确写出来，而不是把猜测包装成定论。

## 工作流示意

```text
User Bug Report
  -> fix-issue-orchestrator (command)
  -> bug-triage (skill)
  -> frontend-reviewer / backend-reviewer / accessibility-reviewer / e2e-reviewer
  -> Repair Summary
```

也可以理解为：

```text
问题描述
  -> 重新表述问题
  -> 找到最可能入口
  -> 沿链路收敛根因
  -> 调对应 reviewer 做风险判断
  -> 输出修复方案和测试建议
```

## 什么时候适合用这个 workflow

以下场景很适合：

- 用户描述比较模糊，需要先收敛问题
- 问题可能跨前端、接口、数据层
- 修复前需要判断风险和影响面
- 希望先拿到“最小安全修复方案”
- 需要沉淀一份可供工程评审使用的问题分析

## 什么时候可以简化

以下场景可以不必走完整流程：

- 明确的拼写错误或文案错误
- 非常局部的样式问题
- 已经有稳定复现和明确根因的小 bug
- 不涉及链路扩散和行为不确定性的微小修复

这时直接用更轻量的 command 或直接修改可能更合适。

## 推荐实践

- 先收敛问题，再动手修
- 优先最小改动，不轻易扩大范围
- 把“已确认”和“推测”明确分开
- 如果存在多个候选根因，按概率排序
- 测试建议尽量最小但有效
- 输出时一定保留未验证项

## 总结

这个 workflow 的核心价值，不是把修 bug 变慢，而是减少“误判根因后继续放大改动”的概率。

如果把职责压缩成一句话：

- `fix-issue-orchestrator` 负责组织排查流程
- `bug-triage` 负责把问题链路收敛清楚
- 各类 reviewer 负责从专业视角判断修复方案是否稳妥
- 最终输出负责把根因、修复、测试和风险边界说清楚
